## Что такое CLR

**Corpus Latino-Rossicum** — параллельный корпус классических латинских текстов с
русскими переводами, дополненный морфологической разметкой и расширенными средствами
поиска. Проект Института лингвистических исследований РАН (ИЛИ РАН), Отдел
сравнительно-исторического изучения индоевропейских языков и ареальных исследований +
Отдел цифрового развития лингвистических проектов.

- Сайт: <https://clr.iling.spb.ru/>
- Описание на сайте ИЛИ РАН: <https://iling.spb.ru/node/1215>
- Команда (по странице ИЛИ РАН): Н. Н. Казанский, М. Л. Кисилиер, И. М. Егоров,
  Е. А. Ботвинева, Д. В. Суховольская
- Разработчик платформы (по подвалу сайта): GitHub-аккаунт `@KIWIbird717`
- © ИЛИ РАН, 2025

Назначение (формулировка проекта): дать «гибкие алгоритмы поиска и анализа», чтобы
исследовать рецепцию античной литературы в русской культуре — корпус построен на
переводах, «вошедших в русскую культуру» (т. е. на канонических, а не любых переводах —
прямая параллель с тем, как этот репозиторий фиксирует «лучшие»/устоявшиеся переводы
Рамаяны и Махабхараты, а не любые доступные).

## Типология Казанского, применённая к CLR (уже задокументировано в этом репозитории)

Это единственный содержательный аспект CLR, для которого в репозитории уже было
прямое источниковедческое расследование (не переоткрываю, а фиксирую ссылку):
[tronsky-XXX/archive/Kazanskiy-typology.md](https://github.com/gasyoun/CommentaryStrategies/blob/main/tronsky-XXX/archive/Kazanskiy-typology.md).
Ключевой вывод: Казанский **не изобретает** типологию комментария для CLR, а **применяет**
стандартную номенклатуру классической филологии (Boeckh 1877; отеч. текстология —
Томашевский/Лихачев/Рейсер): грамматический (филологический) / исторический /
антикварный-реальный (поясняющий реалии) / литературный. Это уже отражено в оси 2 схемы
разметки этого проекта — см.
[docs/TYPOLOGY_GREEK_SANSKRIT.md](https://github.com/gasyoun/CommentaryStrategies/blob/main/docs/TYPOLOGY_GREEK_SANSKRIT.md)
§1 и вывод «интеграция с CLR» в §«Открытые вопросы» того же документа.

## Интерфейс — что удалось изучить напрямую (01.08.2026, WebFetch)

Сайт — JS-приложение (SPA); статический fetch не рендерит динамическое содержимое
(список текстов библиотеки, результаты поиска, постраничное отображение оригинал↔перевод).
Ниже — то, что видно в статической разметке страниц `/ru/search`, `/ru/library`,
`/ru/about`:

### Раздел «Поиск» (`/ru/search`)

- Верхнее меню: **«Поиск» / «Библиотека» / «О проекте»** — три раздела.
- Переключатель режима поиска: **«Словоформа»** (поиск точной словоформы) vs
  **«Лемма»** (поиск по словарной форме — т. е. есть морфологическая лемматизация,
  подтверждает заявленную «морфологическую разметку»).
- Поле ввода: **«Поисковый запрос»**, кнопка **«Поиск»**.
- Многословный поиск: переключатели **«Quodvis»** (любое из слов) / **«Omnia»**
  (все слова) — латинские термины использованы как UI-лейблы, что стилистически
  соответствует предметной области корпуса.
- Пустое состояние: **«Пока нет результатов поиска»** с инструкцией использовать форму.

### Раздел «Библиотека» (`/ru/library`) и «О проекте» (`/ru/about`)

Список текстов/авторов, разбивка на страницы издания и сам механизм парной пагинации
(как визуально связаны оригинал и перевод — колонками, построчно, по абзацам) **не
поддаются извлечению статическим fetch**: это клиентски рендерящийся список/просмотрщик
текста, не присутствующий в исходном HTML. Раздел «О проекте» на самом сайте не содержит
методологического описания разметки/пагинации сверх той же общей формулировки, что и на
странице ИЛИ РАН. RSC-запрос к `/ru/library` (заголовки `RSC: 1`) в этом проходе вернул
**Internal Server Error** — серверный flight payload тоже не дал списка текстов.

### Стек и API (дополнение 01-08-2026, Grok 4.5)

| Наблюдение | Доказательство |
|---|---|
| **Next.js App Router + Turbopack** | HTML грузит `/_next/static/chunks/…` + `turbopack-*.js` |
| **Клиентский data-layer: TanStack Query** | Бандл `d19d6b84a02920a1.js` экспортирует `QueryClientProvider` / `useQueryClient` |
| **Типографика** | Charis SIL (заголовки) + Inter (тело) — `font-charis-sil` / `font-inter` в UI-бандле |
| **Публичного REST API нет** | Пробы `GET /api`, `/api/texts`, `/api/search`, `/api/library`, `/_next/data` → либо 404, либо HTML-оболочка SPA (~41–52 KB), не JSON |
| **Поиск — клиентский** | `GET /ru/search?query=homo&mode=lemma` возвращает ту же SPA-оболочку; результаты не в HTML |
| **Контакт** | `mailto:iliran@mail.ru` в подвале; org-страница ИЛИ РАН: [iling.spb.ru/node/1215](https://iling.spb.ru/node/1215) |

Следствие для §4.2 п.2–3: «адаптировать парную пагинацию» и «прототип поиска» **нельзя**
сделать поверх открытого API CLR — только (а) headless-браузерный осмотр UI + reverse-engineer
приватных эндпоинтов, или (б) договорённость с командой ИЛИ РАН. Вариант (б) уже в очереди
как «CLR-контакт (Казанский)».

## Открытые вопросы (не решаются в рамках этого пункта)

1. **Модель парной пагинации** (следующий пункт §4.2 roadmap) требует либо (а) осмотра
   через реальный браузер / headless-рендеринг SPA, либо (б) прямого контакта с командой
   CLR — что уже отдельно зарегистрировано как «CLR-контакт (Казанский)» в
   [.ai_state.md](https://github.com/gasyoun/CommentaryStrategies/blob/main/.ai_state.md)
   и как data-gated пункт в
   [docs/ROADMAP_2026H2.md](https://github.com/gasyoun/CommentaryStrategies/blob/main/docs/ROADMAP_2026H2.md).
   Человеку стоит решить, кто устанавливает контакт (Казанский — главный редактор журнала,
   где подавалась статья Тронских чтений, т. е. контакт уже частично «тёплый»).
2. Нет открытого API/экспорта данных CLR, обнаруженного в этом проходе — репозиторий
   разработчика (`@KIWIbird717`) не найден веб-поиском как публичный; если у CLR нет
   публичного API, прототип поиска (третий пункт §4.2) либо ограничится собственным
   индексом этого проекта, либо потребует явного разрешения от ИЛИ РАН на доступ к данным.

## Вывод для §4.2

Интерфейс CLR **изучен на доступную глубину** (структура поиска, лемматизация,
типология комментария, команда, назначение корпуса, стек Next.js/TanStack Query,
отсутствие публичного JSON API). Глубже — до уровня «как устроена парная пагинация
текст↔перевод» — статический просмотр и RSC-flight упираются в SPA/сервер; это
не блокирует закрытие текущего пункта чек-листа, но прямо формирует объём следующего
(«адаптировать модель парной пагинации») как **contact-gated** (или headless-browser
с согласием владельца), а не как чисто инженерную задачу поверх открытого API.
